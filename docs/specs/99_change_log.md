# 99_change_log Spec

- 版本: v0.1（草案，待审查）
- 目录: `docs/specs/`
- 角色: 记录项目 Spec 集的版本历史、变更日志明细与未决问题清单；是 Agent 长程执行时防止上下文漂移的上下文锚点
- 依赖: 所有文档（`00`-`90`）

## 文档目的

本文件是管理型文档，不涉及具体的物理或网络细节，但它是整个项目长期迭代、防止 Agent 上下文漂移的核心保障。它的作用有三个：一是版本追溯，记录 Spec 的每一次修改，确保「为什么这么改」有据可查；二是问题追踪，记录实验中发现的未决问题（Open Questions），防止遗忘；三是作为 Agent 上下文锚点，在长程任务中 Agent 通过读取本文件即可快速了解项目当前处于什么状态、哪些规则已被修改。

---

## [S1] 文档结构与组成部分

`99_change_log.md` 包含三个主要部分：

1. **版本历史 (Version History)**：记录项目 Spec 的整体版本演进。
2. **变更日志明细 (Change Log Details)**：每次修改 Spec 文件时在此新增一行记录。
3. **未决问题清单 (Open Questions)**：记录实验中发现的、尚未解决的问题。

### Claims

- C1: 本文件 SHALL 包含版本历史、变更日志明细、未决问题清单三个组成部分，缺一不可。
- C2: 本文件 SHALL 记录 Spec 集的每一次修改，使每次修改的动机与内容有据可查。
- C3: 本文件 SHALL 记录实验中发现的未决问题，防止问题在 Agent 上下文截断后丢失。

版本历史记录项目 Spec 的整体版本演进，采用以下表格：

| 版本号 | 日期 | 状态 | 说明 |
|---|---|---|---|
| v0.1 | 2026-08-24 | Draft | 从对话记录整理为 00-99 多文档结构（草案）；待用户审查后冻结 |

审查通过后，将新增 v1.0（Released）行并标记冻结。

### Claims

- C1: 每次 Spec 版本升级（如 v0.2 → v0.3）SHALL 在版本历史表中新增一行。
- C2: 版本历史表的新增行 SHALL 包含版本号、日期、状态、说明四个字段。
- C3: 状态字段 SHALL 按 Draft → Approved → Released 演进，其中 Released 表示正式交付 Agent 执行。

## [S5] Agent 执行时的更新规则

为了保证 Change Log 的有效性，Agent 在执行时必须遵守以下规则：

1. **先记录，后修改**：在修改任何 Spec 文件之前，必须先在 `99_change_log.md` 中创建一条 `Proposed` 记录；用户或 Supervisor 批准后，状态改为 `Approved`，然后才能修改 Spec。
2. **实验异常必须记录**：如果实验中出现严重物理幻觉（如 $\varepsilon_z$ 误差 > 50%），必须记录到 Open Questions。
3. **版本升级必须同步**：每次 Spec 版本升级（如 v0.2 → v0.3），必须更新 Version History 表格。
4. **禁止直接覆盖**：不允许直接修改 Spec 文件而不记录 Change Log。
5. **每次只修改一个模块**：一次迭代只改一个 Spec 文档（经用户批准的审查批次修订视为一次迭代，仍须在变更日志明细中逐模块记录）。
6. **每次迭代必须有验收结果**：修改后必须给出对应验收证据。

### Claims

- C1: Agent 在修改任何 Spec 文件之前 SHALL 先在 `99_change_log.md` 中创建 `Proposed` 记录；未经用户或 Supervisor 批准（状态未改为 `Approved`）SHALL NOT 修改 Spec 文件。
- C2: 实验中出现的严重物理幻觉（$\varepsilon_z$ 相对误差 > 50%）SHALL 记录到未决问题清单。
- C3: 每次 Spec 版本升级 SHALL 同步更新版本历史表。
- C4: 未在 `99_change_log.md` 中记录变更日志的 Spec 修改 SHALL NOT 发生。

## Decisions

### D1: 变更日志采用 Markdown 表格

**Chosen:** 版本历史、变更日志明细、未决问题清单均使用 Markdown 表格记录，字段固定。
**Rationale:** Markdown 表格便于阅读与版本控制，且 Agent 容易解析；字段固定使每条记录结构一致、可校验完整性。
**Rejected:**
- 自由文本或非表格形式记录变更 — Agent 解析不稳定，字段缺失时无法校验记录完整性。

### D2: 强制「先记录，后修改」

**Chosen:** 修改任何 Spec 文件前，必须先在 `99_change_log.md` 中创建 `Proposed` 记录，批准后改为 `Approved` 才能修改 Spec；禁止直接覆盖。
**Rationale:** 防止 Agent 长程任务中的上下文漂移，保证「为什么这么改」有据可查；与 `00` [S9] 的变更规则一致。
**Rejected:**
- 仅作建议性约定、不强制记录 — 长程任务中 Agent 容易跳过记录步骤，版本追溯与审核失去依据。

### D3: 未决问题必须包含 Resolution 字段

**Chosen:** 每条未决问题记录必须包含 Resolution 字段并填写解决方案或结论，确保每个问题闭环。
**Rationale:** 确保问题有最终结论（已解决或明确留待后续实验），防止问题悬而不决、反复出现。
**Rejected:**
- Resolution 字段可选 — 允许留空会导致问题无人跟进，与「问题追踪、防止遗忘」的文档目的相悖。
